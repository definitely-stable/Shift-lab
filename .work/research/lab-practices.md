# Практики воспроизводимой лаборатории Shift-lab

Проверено: **2026-10-04**. Это исследовательская рекомендация для Delsk/Shift-lab, не утверждённая политика и не результат бенчмарка. Измерения в рамках исследования не запускались. Все будущие бенчмарки выполняются в GitHub CI; локальная машина используется для подготовки и проверки документов, кода и уже полученных данных. Численные бюджеты ниже — предлагаемые ограничения проекта, а не гарантии GitHub.

Определения метрик, порядок измерений и gates берутся из [DELSK-P1](../protocol.md), а operational caps и evidence bundle — из [CI-плана](../ci-plan.md). Этот обзор объясняет их основания и не создаёт альтернативного протокола. Численные policy замораживаются после baseline pilot, до candidate evaluation, вместе с issue, commit и locks.

## 1. Что перенять из ChunkShift

Изучен фактический checkout `definitely-stable/ChunkShift` на коммите `489d3f2fe2582cc6251ee2fa87cd23bad1793b01`. Его правила рассматриваются как опыт другой лаборатории: API, форматы, названия экспериментов, релизные требования и полномочия сопровождающих автоматически на Shift-lab не распространяются.

Полезна компактная цепочка `issue → experiment → run → evidence → решение`. В ChunkShift гипотеза имеет стабильный идентификатор, конкретное исполнение связывается с коммитом, окружением и отпечатком протокола, а итоговое решение отдельно описывает включённые данные, исключения и ограничения. Отрицательные результаты сохраняются. Для Shift-lab достаточно одного индекса, одного файла протокола на вопрос и одного отчёта на решение; отдельная база данных пока не нужна. [README исследований](https://github.com/definitely-stable/ChunkShift/blob/489d3f2fe2582cc6251ee2fa87cd23bad1793b01/docs/research/README.md), [шаблон результата](https://github.com/definitely-stable/ChunkShift/blob/489d3f2fe2582cc6251ee2fa87cd23bad1793b01/docs/research/RESULT-TEMPLATE.md).

Хорошо разделены корректность и скорость. Политика производительности ставит сохранение семантики выше ускорения, требует учитывать аллокации, копирование и память и не устанавливает вечный процент регрессии до калибровки шума. Для новой лаборатории это означает: сначала oracle и воспроизводимый корпус, затем сравнительная производительность. Изменение границ чанков, формата или идентичности результата исследуется как отдельная гипотеза, а не маскируется под оптимизацию. [PERFORMANCE.md](https://github.com/definitely-stable/ChunkShift/blob/489d3f2fe2582cc6251ee2fa87cd23bad1793b01/docs/PERFORMANCE.md).

Практический протокол `PATCH-ENC-005` использует пять раундов с baseline до и после кандидатов, вращает порядок кандидатов, раздельно считает wall/CPU, выделяет память в отдельные процессы. Нестабильный baseline делает данные неполными, а не автоматически хорошими или плохими; повтор ограничен. Переносим структуру сравнения, но не его 25% границу шума, пять раундов или предметные пороги: они выбраны для конкретного эксперимента. [Протокол, §9](https://github.com/definitely-stable/ChunkShift/blob/489d3f2fe2582cc6251ee2fa87cd23bad1793b01/docs/benchmarks/PATCH-ENC-005-PROTOCOL.md#9-decision-metrics-and-paired-timing).

Особенно полезен отрицательный пример: H7 нарушил byte oracle на 83 из 1049 файлов; отчёт сохранил контрпримеры, частичные измерения и явно отказался выводить ускорение из одного раунда. Другой результат сохраняет отдельные повторения, контрольные суммы и независимый `recompute.py`, позволяющий восстановить решение после истечения CI-артефактов. [Неполная калибровка](https://github.com/definitely-stable/ChunkShift/blob/489d3f2fe2582cc6251ee2fa87cd23bad1793b01/docs/research/results/PATCH-ENC-005-EVIDENCE-20261003-001.md), [воспроизводимый итог PATCH-APPLY-003](https://github.com/definitely-stable/ChunkShift/blob/489d3f2fe2582cc6251ee2fa87cd23bad1793b01/docs/research/results/PATCH-APPLY-003-EVIDENCE-20260930-001.md).

## 2. Что нельзя копировать без адаптации

`patch-lab.yml` запускается вручную, содержит многочисленные группы, трёхплатформенные проверки и лимиты jobs до 350 минут; артефакты удерживаются 90 дней. `benchmark-lab.yml` сочетает smoke, короткие измерения и специализированные jobs до 240 минут. Это развитый стенд со значительной эксплуатационной стоимостью. Для пустой лаборатории такие матрицы преждевременны. Полезны pinned action SHA, минимальные разрешения, загрузка свидетельств после ошибки и проверки полноты; размеры матрицы надо уменьшить. [Patch workflow](https://github.com/definitely-stable/ChunkShift/blob/489d3f2fe2582cc6251ee2fa87cd23bad1793b01/.github/workflows/patch-lab.yml), [Benchmark workflow](https://github.com/definitely-stable/ChunkShift/blob/489d3f2fe2582cc6251ee2fa87cd23bad1793b01/.github/workflows/benchmark-lab.yml).

Обнаруженные ограничения — основания для улучшения, не обвинения:

- `workflow_dispatch` от позднего `main` не воспроизводит старый измеренный коммит; нужно явно фиксировать обе версии и SHA workflow/harness.
- Совпадение hash результата подтверждает лишь заявленную идентичность; оно не заменяет независимый decoder, проверку границ и семантические свойства.
- Короткая последовательность повторов в одном процессе не характеризует различия между хостами и холодными запусками.
- Вычитание idle RSS полезно для диагностики, но абсолютный peak RSS нужен отдельно: именно он определяет возможность запуска на ограниченном устройстве.
- Полный реестр незавершённых идей не равен доказанной программе работ. В Shift-lab активны только эксперименты с измеримым вопросом и ресурсным бюджетом.

Эти выводы получены сопоставлением перечисленных протоколов, workflow и evidence; они не являются требованиями авторов ChunkShift.

## 3. Документированные возможности GitHub CI

Для публичных репозиториев стандартные `ubuntu-24.04` и `ubuntu-24.04-arm` документированы как Linux x64/ARM64 с **4 CPU, 16 GB RAM, 14 GB SSD**. Стандартные VM создаются заново для jobs. Это доступность архитектур и класса ресурсов, не обещание одной модели CPU, одинаковой частоты, дисковой задержки или свободных 14 GB после подготовки окружения. `ubuntu-latest` не фиксирует образ; даже версия ОС требует записывать конкретную версию runner image. [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

Стандартные hosted runners для публичных репозиториев бесплатны; larger runners оплачиваются даже для публичных репозиториев. Публичный compute нельзя трактовать как бессрочное безлимитное хранилище: документация отдельно описывает artifact storage, общий с Packages, и cache allowance; для Free в таблице указаны 500 MB артефактов и 10 GB cache. Перед внедрением требуется проверить фактический план и настройки владельца, не обещая нулевую стоимость любого объёма хранения. [Биллинг Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

Документированный максимум hosted job — 6 часов; Free допускает 20 одновременных standard jobs. Это верхние пределы сервиса, а не разумный бюджет лаборатории. [Actions limits](https://docs.github.com/en/actions/reference/limits).

Для публичных репозиториев retention настраивается в пределах **1–90 дней**. Документация сообщает, что с **2026-10-01** эта политика относится также к checks, workflow runs и commit statuses. Поэтому даже ссылка на успешный запуск может перестать быть доступной: сохраняем идентификаторы, provenance и данные независимо от UI GitHub. [Retention policy](https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization).

## 4. Предлагаемые уровни CI и бюджеты

Начальный стенд ориентирован на Linux; Windows и macOS добавляются только при отдельном вопросе о переносимости. ARM64 используется нативно, эмуляция не выдаётся за производительность ARM. Следующие величины — **проектные ceilings**, подлежащие пересмотру после пилота.

| Уровень | Когда и зачем | Матрица и потолок | Данные и хранение |
|---|---|---|---|
| Smoke | PR; schema, oracle, детерминизм, сборка | x64, 1 job × 8 минут | ≤64 MiB корпуса; artifact ≤2 MiB, 7 дней |
| Pilot | Ручной dispatch; исполнимость, A/A noise, отбор | x64, 1 × 30 минут | acquired ≤256 MiB, materialized ≤1 GiB; ≤4096 pairs/codec; ≤10 MiB результата, 30 дней |
| Decision | Ручной dispatch по замороженному протоколу | x64 + ARM64, 2 × 45 минут; summary ≤5 минут | materialized ≤2 GiB/job; ≤20k pairs/codec/job; ≤20 MiB на архитектуру + ≤5 MiB summary, 90 дней |
| Confirmation | Второй независимый Decision выбранного кандидата | тот же потолок 95 runner-minutes | тот же frozen lock без tuning; новый run id; retention 90 дней |

Smoke не блокирует PR по времени выполнения алгоритма: в нём нет точного performance verdict. Для решения требуются два независимых CI запуска, а не две последовательности на одном хосте. Очередь архитектур ограничивается `max-parallel: 2`; внутри измерения baseline и candidate выполняются последовательно. Отменять устаревшие PR smoke можно, прерывать уже начатое подтверждение новым push не следует.

Предлагаемый недельный бюджет — **600 runner-minutes на экспериментальные dispatch**, включая сумму длительностей jobs, подготовку, неудачи и повторы. PR smoke и docs check имеют отдельные короткие caps и в этот экспериментальный бюджет не входят. Пример: 4 pilot × 30 + 2 пары decision/confirmation × 190 = 500 минут; остаток 100 минут — резерв. Это не тариф GitHub. CI-план предусматривает reservation перед dispatch и учёт durations; текст сам лимит не обеспечивает. Если сборка или корпус не помещаются, сокращают заранее объявленный набор условий, а не незаметно число повторений финального опыта. Retention ограничивается фактической repository policy.

Для каждого benchmark job: один исследуемый процесс за раз; основной режим один worker, параллельность `2/4` — отдельный фактор; лимит дерева процессов 4 GiB RAM; суммарные corpus/temp/output ≤6 GiB; стартовая проверка свободного диска ≥8 GiB. Harness прекращает работу при достижении лимита, фиксируя `resource_exceeded`; память ограничивается доступным механизмом ОС, а его отсутствие записывается как ограничение исполнения. Данные скачиваются и проверяются до таймера. Совокупные временные артефакты лаборатории ограничиваются 300 MiB, cache — 2 GiB; при заполнении сначала сохраняют compact evidence, затем удаляют истёкшие временные результаты.

## 5. Парное измерение и честный вывод

До dispatch фиксируются гипотеза, baseline/candidate SHA, корпус, режим cache, порядок, число повторов, метрики, правила исключения, практический минимальный эффект и пределы ресурсов. На pilot измеряется **A/A**: один и тот же код проходит всю процедуру сравнения как две версии. Это оценивает шум самого стенда, а не выигрывает конкурс алгоритмов. Шумовой порог утверждается после pilot, до Decision; универсальное «быстрее на 5%» заранее не принимается.

Стартовая процедура DELSK-P1: **два warm-up rounds**, исключаемых из итоговых timing, затем **пять** измеряемых paired blocks `A → B → A`. Порядок кандидатов между blocks детерминированно перемешивается и сохраняется. Отношение wall кандидата к среднему двух соседних wall baseline считается в каждом блоке; CPU ratio рассчитывается отдельно. В отчёте показываются все ratios, медиана и разброс, абсолютные время и throughput. Число блоков — начальная policy, не статистическая гарантия; после pilot оно фиксируется в основном протоколе.

Предпочтение соседних сравнений и перемешивания согласуется с практикой Google Benchmark, где interleaving уменьшает влияние изменяющегося состояния системы. Частоты CPU и ASLR названы источниками вариативности; на hosted VM нельзя предполагать возможность управлять физическим хостом. [Random interleaving](https://github.com/google/benchmark/blob/main/docs/random_interleaving.md), [Reducing variance](https://google.github.io/benchmark/reducing_variance.html).

Отдельно проверяются холодный запуск и steady state, если они входят в вопрос. Операции внутри одного процесса, файлы одного корпуса и разные VM не считаются автоматически независимыми наблюдениями. Timing uncertainty учитывает блоки/запуски; quality intervals используют lineage cluster bootstrap из DELSK-P1, а не timing repetitions. Опубликованная ширина интервала не обещает переносимость на другие CPU. При слишком малом числе независимых запусков timing остаётся описательным. P95 regret по targets и p95 времени по пяти blocks — разные статистики; последнее не служит точным tail estimate. Обоснование различать источники вариативности и стоимость повторений: [Kalibera–Jones, ISMM 2013](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf).

Шум не лечится выбором лучшего запуска. Начальная policy DELSK-P1: если baseline brackets расходятся более чем на 10% в более чем одном из пяти blocks, timing run получает `INCONCLUSIVE`; отдельные медленные blocks не удаляются. Валидные quality bytes сохраняют пригодность при соблюдении provenance/correctness. Любой повтор получает отдельную запись, confirmation — новый run id; retry policy входит в freeze. Decode mismatch делает run `INVALID`; отрицательный корректный результат — `REJECT`. Проходящий кандидат удовлетворяет gates основного протокола на заявленных domains и архитектурах; отсутствие доказанной регрессии не тождественно доказанному ускорению.

## 6. Корпус, метрики и внешние ориентиры

Сравнение дедупликации должно включать throughput, размеры чанков и итоговое сокращение данных. DedupBench университета Waterloo полезен разделением chunking и fingerprinting, явными параметрами размера и отдельными SIMD-сборками. Его README предупреждает: random dataset даёт нулевую экономию; непригодная ISA может приводить к ошибкам. Поэтому случайные байты годятся для технического smoke, но не заменяют версии реальных файлов. Использовать DedupBench как внешний comparator следует с фиксированным SHA, одинаковыми параметрами и явно указанным составом измеряемого pipeline. [UWASL/DedupBench](https://github.com/UWASL/dedup-bench).

Практический минимум корпуса: несколько независимо версионируемых семейств, обычные и сжатые данные, повторяющиеся/низкоэнтропийные входы, вставки/удаления/перестановки, маленькие и крупные файлы. Размеры выборок и seed фиксируются заранее; development/calibration/evaluation разделяются **по lineage**, включая связанные transformed variants. Разделение только по версиям одной семьи не соответствует DELSK-P1. При менее 10 независимых held-out lineages на domain вывод exploratory. Итог включает результаты по каждому семейству, суммы bytes и время обработки workload; одно среднее не должно скрывать проигрывающие классы. Для patch pipeline дополнительно нужны create/apply wall/CPU, patch bytes, base bytes read, peak RSS и byte-for-byte восстановление target.

От стандартов научных артефактов полезно перенять два маршрута: короткая проверка работоспособности и подробное воспроизведение заявленного результата. FAST ’25 отдельно требует конкретных утверждений, README и процедуры проверки; доступность артефакта, его работоспособность и воспроизведение результата — различные свойства. Shift-lab может применять эту структуру внутренне, не заявляя получение научного badge. [USENIX FAST ’25 artifact evaluation](https://www.usenix.org/conference/fast25/call-for-artifacts).

## 7. Минимальная схема evidence

Имена и состав задаёт evidence bundle v1 в CI-плане: `run.json`, `corpus-lock.json`, `candidate-lock.json`, `tools.json`, `pairs.jsonl`, `targets.jsonl`, `timings.jsonl`, `coverage.json`, `summary.json`, `verdict.json`, `checksums.sha256`. Они сохраняются в `.work/results/<experiment>/<run-id>/`; рядом нужны человекочитаемый evidence record и воспроизводимый evaluator. Версия schema обязательна; строки измерений хранят единицы и связь с run/block/workload. Области обязательных сведений:

| Область | Обязательные сведения |
|---|---|
| Идентичность | experiment id, issue, run/attempt/job id, UTC, baseline/candidate SHA, harness/workflow SHA, clean-tree state |
| Протокол | digest определения, роли calibration/evaluation/confirmation, seed, порядок, warmup, planned/completed repetitions |
| Окружение | runner label и image version, ОС/kernel, architecture, CPU model/features/logical count, SDK/runtime/compiler, build flags |
| Корпус | происхождение и лицензия, version URL, archive/file digests, materializer SHA, выбранный manifest и его digest |
| Наблюдения | raw wall/CPU, processed/output bytes, RSS absolute/idle, allocations при доступности, cache mode, exit status, oracle status |
| Качество | пропуски, исключения с причинами, ресурсные нарушения, noise flags, доступность аппаратных counters |
| Итог | effect и uncertainty, правило агрегации, ограничения, решение, ссылки на compact data и временные artifacts |

Compact evidence в Git сохраняет **все** использованные измерения и сведения об исключённых запусках; сокращаются логи и payload, а не неудобные samples. Большие корпуса остаются вне Git с digest, лицензией и точной рецептурой. Артефакт digest защищает идентичность скачанного файла, но сам по себе не доказывает корректность замера. Независимый recompute восстанавливает таблицы и решение без повторного бенчмарка. Отсутствующее значение записывается как `null` с причиной, никогда как ноль.

## 8. Очерёдность внедрения

1. Создать schema и tiny corpus, реализовать oracle и проверку полноты отчёта; подтвердить их в CI smoke.
2. Выполнить ограниченную A/A calibration на GitHub runners; зафиксировать шум, стоимость сборки и допустимый объём корпуса.
3. Выбрать один исследовательский вопрос и baseline; заморозить протокол и holdout до выбора кандидата.
4. Получить два независимых парных CI запуска, сохранить compact evidence, воспроизвести итог агрегатором.
5. Лишь затем расширять архитектуры, число кандидатов или корпус по выявленным ограничениям.

До этих шагов ни для одного метода не установлено преимущество. Начальная ценность лаборатории — проверяемое различие между «работает», «измерено», «достаточно данных» и «стоит внедрять» при ограниченных ресурсах.
