## Что это значит

- Стоимость выбора базы пренебрежимо мала рядом с самим delta-кодированием. Запрос к индексу — десятки µs. Одна пара encode + decode xdelta3 в X0 (медианы по retained `pairs.jsonl`): ≈ 5 ms для chunks 16 KiB, 50 ms для исходников, 677 ms для бинарников в мегабайты. При K = 2 selector экономит 10–21 вызов кодера на target ([README §4](README.md)).
- Память: 64 B descriptor + ≈ 41 B индекса на объект. Peak RSS включает ещё строковые id и метаданные benchmark: 419 MB на 10⁶ объектов, то есть ≈ 420 B на объект в этом прототипе. Компактное хранение id — работа интеграции.
- Индекс с cap 64 — разумное значение по умолчанию: оно в 4 раза больше популярных posting lists этой нагрузки и на два порядка дешевле полного перебора.

## Ограничения

- Нагрузка synthetic. Совпадение индекса с полным перебором доказано только на ней. Распределение популярности хэшей в реальном каталоге (общие лицензии, vendored код, пустые блоки) может быть тяжелее, и cap тогда отрежет нужные объекты. Это нужно проверить на реальном каталоге в S4.
- Один runner, один run. Timing описательный: это не гарантия latency для других CPU или для нагрузки с конкуренцией.
- Качество выбора относительно oracle здесь не измерялось. Оно — в [README §4](README.md) (in-sample).
