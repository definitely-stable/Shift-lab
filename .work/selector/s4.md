# S4: ChunkShift consumer integration — preregistered development screen

Status: **PREREGISTRATION / NOT_RUN**.  
Owner: [DELSK-012](https://github.com/definitely-stable/Shift-lab/issues/13).  
Selector: [`delsk.simple-selector.v1`](README.md).  
Consumer pin: [`chunkshift-consumer.json`](chunkshift-consumer.json).

S4 answers one narrow question:

> Does the already-adopted simple Delsk selector improve a real ChunkShift patch-building workflow enough to justify carrying it beyond Shift-lab?

This slice freezes the development screen before any S4 ChunkShift patch bytes are measured. It does **not** change Delsk v1, ChunkShift production defaults, CSP/CSM, or public APIs.

## 1. Integration boundary

Delsk and ChunkShift have two different candidate-selection layers and S4 must not conflate them.

- **Delsk layer:** choose which prior **whole content objects / versions** should be tried as the base for one target object.
- **ChunkShift layer:** once a base object has been chosen, `ChunkPatch.CreateAsync` internally chooses per-target-chunk dictionary windows using the pinned production `CspEncoderPolicy.Default`.

S4 changes only the outer layer. Every lane invokes the exact same pinned ChunkShift public CLI and therefore the same internal chunking, dictionary search, zstd settings, CSP v1 writer and apply path.

Forbidden interpretations:

- a Delsk base object is not a ChunkShift dictionary-window start;
- PATCH-ENC-005 H6-O/resemblance is not the Delsk selector;
- S4 may not install `ICspResearchCandidateSelector` or another ChunkShift internal research selector;
- an internal ChunkShift candidate-policy change invalidates the run instead of becoming a hidden S4 variable.

## 2. Population and information boundary

The development population is the already-burned data used by the simple selector:

1. pilot-v1 **development + calibration** near-duplicate queries;
2. all four X0 screening cells.

The sealed pilot evaluation split is not opened. S4-D therefore cannot close G5 or make a held-out product claim.

The candidate universe for a target is exactly its already-frozen Delsk `C_t`. No new base is added because it happens to work well under ChunkShift.

Natural payload bytes are re-materialized only inside the GitHub-hosted runner and are not committed. Retained S4 evidence contains metadata, digests, timings and result rows, not source payloads or CSP files.

## 3. Frozen lanes

Every target always gets one self-contained ChunkShift patch. Base-dependent lanes add the following base-object trials:

| lane | base objects tried |
|---|---|
| `previous1` | first strong metadata baseline: pilot `previous_version`; X0 `version_previous` |
| `size1` | first `size_closest` base |
| `delsk2` | first 2 bases of the already-adopted `delsk.simple-selector.v1` order |
| `delsk4` | first 4 bases of the same order |
| `exhaustive` | every base in the frozen `C_t`; diagnostic system oracle only |

If `|C_t| < K`, the lane tries all available bases. Duplicate object IDs in a lane are forbidden.

The result for one target/lane is the smallest physical CSP byte count among its self-contained patch and all base-dependent patches attempted by that lane. Ties are broken only for reporting by the lexical base object id; byte totals are unaffected.

S3 is binding: **no abstention is allowed**. `L = 0`.

## 4. What is measured

For every unique target/base pair needed by `exhaustive`:

- physical CSP bytes;
- create wall and child CPU time;
- apply wall and child CPU time;
- exact target SHA-256 after apply;
- ChunkShift target/base manifest ids;
- exit status and error class.

For each target, one self-contained patch is measured the same way.

Separately retain:

- ChunkShift checkout SHA and CLI build identity;
- manifest-build wall/CPU;
- Delsk descriptor/index construction cost;
- total object bytes scanned for descriptors;
- lane candidate-call counts;
- runner/image/toolchain provenance.

A patch that fails to apply byte-for-byte to the target makes the S4 run **INVALID**. Failed/cancelled pair measurements cannot be silently omitted.

## 5. Derived system quantities

For lane `L` and target `t`:

`A_L(t) = min(self_contained(t), patch(base,t) for base in selected_L(t))`.

`O_CS(t) = A_exhaustive(t)`.

Aggregate physical bytes:

`B_L = Σ A_L(t)`.

System SavingsCapture:

`SC_L = Σ(S_CS(t)-A_L(t)) / Σ(S_CS(t)-O_CS(t))`,

where `S_CS` is the self-contained ChunkShift patch. If the denominator is zero, `SC` is `N/A` and cannot pass the screen.

Candidate-create reduction:

`R_calls(L) = calls(exhaustive) / calls(L)`,

including the one self-contained create in both numerator and denominator.

Cold descriptor/index build cost is reported separately from per-target query and patch-create cost. No amortization claim is made without an explicit query count.

## 6. Preregistered development-screen decision

This is a screen, not G5.

Let `B_control = min(B_previous1, B_size1)`.

A Delsk lane is **eligible for fresh confirmation** only if all are true:

1. exact reconstruction passes for every measured patch;
2. `SC >= 0.98`;
3. aggregate physical bytes are no worse than `B_control + 0.5%`;
4. aggregate physical bytes improve on `B_control` by at least **0.5%**, because Delsk tries more bases than either one-base control and otherwise has no demonstrated system value;
5. candidate-create reduction versus exhaustive is at least **4x**;
6. no population (pilot-development, pilot-calibration, or any X0 cell with a non-zero oracle-savings denominator) loses more than **2 percentage points** of SavingsCapture versus the better one-base control for that population.

The candidate for confirmation is the **smallest K** among `delsk2`, then `delsk4`, that satisfies all conditions.

Possible verdicts:

- `OPEN_CONFIRMATION_K2`
- `OPEN_CONFIRMATION_K4`
- `NO_SYSTEM_SIGNAL`
- `INVALID`

There is no `G5_PASS` verdict in this slice.

If `NO_SYSTEM_SIGNAL`, the default recommendation is to stop pursuing Delsk as a standalone dependency. The retained selector may still remain as a documented heuristic or be reused by a consumer if a separate product-specific case appears.

## 7. Fresh confirmation if the screen passes

A passing development screen opens, but does not define, a separate confirmation protocol.

Before any confirmation payload is inspected, that follow-up must freeze:

- fresh lineages/versions not used to choose Delsk v1 or this S4 screen;
- the winning K;
- paired timing design;
- cold and amortized query counts;
- memory/index bounds;
- final G5 system thresholds;
- independent repeat on a separately allocated GitHub-hosted runner.

No confirmation tuning is permitted from S4-D results.

## 8. Execution constraints

- Standard GitHub-hosted runners only.
- No self-hosted runner.
- No local result can substitute for GitHub evidence.
- ChunkShift must be checked out at the exact consumer pin.
- ChunkShift source must remain unmodified during the run.
- Only the public CLI/public Patching path may create/apply CSP.
- No S4 workflow run is authorized until this preregistration PR is merged.
- The first implementation PR may add a bounded runner/workflow, but it may not change sections 1–6 of this document.

## 9. Why PATCH-ENC-005 does not replace S4

ChunkShift PATCH-ENC-005 asked whether a smarter **within-one-base dictionary-window search** beats its production offset search. Its final evidence is `REJECT / STOP_RESEMBLANCE`.

Delsk S4 asks whether a cheap selector can choose **which base object/version to try in the first place**.

Those are orthogonal layers. S4 deliberately keeps PATCH-ENC-005's production outcome fixed rather than competing with or reopening it.
