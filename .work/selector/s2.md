# S2: стоимость simple selector на большом каталоге

Статус: **RUN** — [результаты](results-s2.md) (run 37455719130): все ориентиры выполнены. Selector — [`delsk.simple-selector.v1`](README.md). Задача — бывшая [DELSK-008](https://github.com/definitely-stable/Shift-lab/issues/9), перенацеленная [решением о pivot](../decisions/2026-10-06-pivot-simple-selector.md).

## Что сделано

- **Rust-прототип** [`rust/`](rust/) без внешних зависимостей:
  - streaming descriptor 64 B;
  - порядок selector;
  - `select_top`: первые K без полной сортировки;
  - `Catalog`: карта `path → объекты` и inverted index по 8 хэшам descriptor с cap на posting list.
- **Parity с Python-эталоном.** [`vectors.txt`](vectors.txt) генерирует `simple_selector.py vectors`: descriptors 9 входов длиной 0–300 000 B, resemblance, 5 случаев выбора. Rust их воспроизводит, порядок кандидатов на входе не влияет. Ещё проверяется, что поток с любым разбиением даёт тот же descriptor, а `select_top` совпадает с полным порядком. CI: `selector-ci.yml` на PR и push.
- **Benchmark** [`delsk-bench`](rust/src/bin/delsk-bench.rs):
  - throughput descriptor на 256 MiB;
  - каталоги из 10⁴, 10⁵ и 10⁶ объектов: семейства по 16 версий объектов 4 KiB; у каждого 32-го семейства общий 1 KiB boilerplate (популярные хэши); каждое 8-е семейство — форк другого; у четверти семейств нет пути;
  - 200 запросов K = 2, полный перебор и индекс с cap 16/64/1024;
  - что выводит: задержка p50/p95, совпадение с полным перебором, число кандидатов, срабатывания cap, память индекса и peak RSS.

## Что это измеряет и чего нет

- Стоимость и согласованность индекса с полным перебором на детерминированной **synthetic** нагрузке. Качество относительно oracle здесь не измеряется: оно проверено в [README §4](README.md) на реальных данных при `C_t` ≤ 64.
- Один поток, scalar код, hosted runner. Числа относятся к конфигурации runner из `run.json`. Сравнивать их с native throughput других систем нельзя.
- Cap обрезает posting list по порядку вставки (старые объекты первыми). Для популярных хэшей это значит, что новые объекты через этот хэш не находятся. На реальном каталоге это нужно проверить отдельно.

## Ориентиры (не gates)

| Величина | Ориентир для интеграции |
|---|---|
| Запрос на 10⁶ объектов, p95, индекс cap 64 | ≤ 1 ms |
| Совпадение top-2 индекса с полным перебором | ≥ 0.99 |
| Индекс сверх 64 B descriptor | ≤ 64 B на объект |
| Throughput descriptor | ≥ 200 MiB/s на поток |

Локальная прикидка (не evidence; машина разработки, 10⁶ объектов): индекс с cap 64 отвечал за p95 ≈ 30 µs против ≈ 150 ms у полного перебора. Top-2 индекса совпадал с полным перебором в 100 % запросов. Индекс занимал ≈ 41 B на объект, descriptor строился на ≈ 500 MiB/s. Evidence — run в Actions: [results-s2.md](results-s2.md).
